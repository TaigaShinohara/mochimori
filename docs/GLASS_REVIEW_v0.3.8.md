# GLASS_REVIEW v0.3.8 — 実機スクリーンショットを受けた見直し（v0.3.9）

対象: v0.3.8 の実機スクリーンショット（ダーク・節電できてる・残量43%、2026-11-19 23:21 本人撮影）
本人の言葉: 「画面がみづらい。もっと見やすくオシャレでシンプルにして。シンプルガラススキルも使って」
あわせて本人の指示: 「液体に関してはパーティクルを使いよりリアルな液体の動きを表現して」→ §4

## 1. スクリーンショットで起きていたこと（根本原因）

1. **Dynamic Color が土台を壁紙色に染めていた**: 土台（AppBackgroundDrawable）の色はテーマロール経由で解決され、MochiApp が DynamicColors を全アクティビティに適用していたため、本人の壁紙（ピンク〜茶系）が primaryContainer / tertiaryContainer に流れ込み、背景全体が「上は暗い茶色、下はピンク」の濁ったグラデーションになっていた。アート方針の「深いネイビー＋柔らかい青白」は画面のどこにも残っていなかった。
2. **下部ナビ裏の光でラベルが消えていた**: 土台の光3つ目が画面下部中央（h×1.02）にあり、下部ナビの真裏で最も明るく光っていた。ナビの帯は読み物ガラス（ダーク 白19%→13%）で薄く、未選択タブ（気づき）のアイコンとラベルがピンクの光に溶けてほぼ視認不能だった。スキル自身の失敗表「補助文字だけ読めない（補助色が薄い＋光が真後ろ）」そのもの。
3. **「数値を見る」が薄かった**: textButton の文字色はテーマの colorPrimary で、Dynamic Color により淡いピンクに解決され、ピンクの背景の上でコントラストを失っていた。

## 2. 直したこと（Simple Glass の型の範囲で）

| # | 変更 | 内容 |
|---|---|---|
| 1 | Dynamic Color を全廃 | MochiApp から `DynamicColors.applyToActivitiesIfAvailable` を削除。アプリ全体が固定パレット（深いネイビー＋柔らかい青白）で描かれる。状態色だけでなく土台も「端末ごとに変わらない」ことが、このアプリの見やすさの前提だと判断した（§1-1 の再発防止） |
| 2 | 土台のグラデーションを1色相に | 3点目を tertiaryContainer（紫）→ secondaryContainer（青灰）に変更。土台に紫・ピンクの色相を持ち込まない。紫は小さなアクセント専用のまま |
| 3 | 光を弱く・位置を直す | 光の alpha 165 → 76（半分以下）。3つ目の光を画面下部中央 → 画面中央（顔の背後）へ移動し、顔のハローとして働かせる。下部ナビの背後には強い光を置かない |
| 4 | バー（上部・下部）の面を「重ね面」の厚さに | GlassDrawable.band を読み物ガラスから重ね面クラスへ変更: テーマの surface 色を ライト 92%→88%／ダーク 95%→90% で敷く。ふちハイライト（スペキュラ）は維持。背後の光の明暗に左右されず文字が読めることが、透け感より優先（スキルの読みやすさの正本どおり、ゲートを満たすために面を厚くする判断） |
| 5 | ナビの色を明示指定 | itemIconTintList / itemTextColor を ColorStateList で明示（選択中=colorPrimary、未選択=colorOnSurfaceVariant）、アクティブインジケータは secondaryContainer を明示。テーマや動的色に委ねない |

主ボタン・進捗・選択中などの役割色ベタは従来どおり（ガラス化しない）。カードの読み物ガラス／役割ティント面は変更なし（今回の問題はバーと土台に局在していた）。

コントラストは色値からの静的計算（最悪条件＝帯の最も薄い下端 × 背後の最も明るい光で合成）:

| 対象 | 前（v0.3.8 実機） | 後（v0.3.9） | 基準 |
|---|---|---|---|
| 下部ナビ未選択ラベル（ダーク） | ピンクの光の上で実質視認不能 | 約 9.6:1（#B4C6D2 × 帯合成色） | 4.5:1 以上 ✓ |

その他のゲート項目は v0.3.8 監査（GLASS_REVIEW_v0.3.7.md）から不変で合格。今回の変更で新たに落ちる項目はない。背景ぼかし未適用（View のプラットフォーム制約）と、その代替（半透明＋縁＋光）も従来どおり。

## 4. 液体のパーティクル化（本人の指示）

BatteryFaceView の液体を、数式の波形描画からパーティクル主体へ作り替えた:

- **液面パーティクルチェーン**: 液面の44サンプル点すべてをパーティクル化。各点が独自のオフセットと速度を持ち、解析波（傾き平面＋進行波）へバネで引き戻されつつ、隣の点とバネ結合する。波紋が液面を伝わり、干渉し合う有機的な動きになる。物理定数: 復元バネ 120、減衰 5.0、隣接結合 260、オフセットは ±9dp でクランプ。
- **飛沫パーティクル（プール24粒）**: バシャバシャのエネルギーで液面から発生し、重力（1500dp/s²）で放物線を描き、器の内壁で跳ね返り（反発 0.45）、着水時に運動量を液面チェーンへ波紋として返す。着水の約3割で小さな二次飛沫が跳ねる。飛行中は速度で縦に伸びる水滴形に描く。全て液体のクリップ内のみ。
- **気泡パーティクル（プール8粒）**: 各粒が自分の位置・上昇速度・揺れを持ち、液面に達したら底から再出現する。従来の決定的サイクル（全粒が同じ位相で動く）ではなくなった。状態別の粒数・速さ（ひんやり3粒ゆっくり／充電7粒／燃焼8粒活発）は従来の意味を維持。
- 波パラメータ（computeWave）を描画と物理で共有し、飛沫は「描かれている液面」に着水する。プールは固定長で、フレームごとの確保はしない。動きを減らす設定では物理時計が止まり、パーティクルは静止画のまま（従来仕様を継承）。触覚の同期仕様も変更なし（バシャバシャの山への同期は splashLevel 経由でそのまま働く）。

## 5. 未確認の範囲

- 実際の見え方（土台の静けさ、帯の厚みの印象、顔のハロー）は実機でしか最終判定できない。コード照合＋静的コントラスト計算＋ビルド＋単体テストまでの確認であり、統一感の判定は仮判定（実機待ち行列）。
- パーティクルの動きの「リアルさ」・気持ちよさも実機（および実際に端末を振る操作）でしか判定できない。物理定数は控えめな初期値で、感想を受けて調整する前提。
